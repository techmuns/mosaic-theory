# Parallel theme universe band — the theme altitude gets megacaps without touching the validation population

**WHAT.** Operator ruling 2026-08-31: a SECOND cap band (`Config.theme_universe`, $10B–$10T, every
other gate identical) built into its OWN snapshot (`theme_universe_snapshot`) and read ONLY at the
theme altitude. `build_universe(..., band_name=)` selects the population; `vinci build-universe
--band theme` builds it; `load_detection_universe` unions it into theme scans **when the file
exists** (presence-gated, the frontend-mirror discipline) with every name carrying `band`
provenance. Screens / ranker / ledger / scoring are untouched — `Store.latest_universe` DEFAULTS to
primary so a decision-path caller cannot opt into the theme band by forgetting an argument.

**WHY PARALLEL RATHER THAN WIDENING THE EXISTING BAND.** The primary $300M–$10B band IS the
forward-validation population: screens, ranker and the BUY−AVOID spread have accumulated against
that membership since the clock started, so widening it mid-flight would change the experiment's
population mid-experiment. The parallel band adds reach without touching the record. The
motivating gap was real and measured: both declared thesis cards name beneficiaries
(MSFT/GOOGL/AMZN/NVDA/LLY/CRM/NOW/VEEV/SAP) that the scan could never assess, so the exposure scan
returned the mid-cap PERIPHERY of each thesis and never its centre. **SCANNABLE IS NOT TRADEABLE**:
a megacap surfaced by a scan still enters the book only through the dossier/underwrite path, where
the MC1–MC4 / FPI1–FPI5 readiness gates bind per name
(`docs/records/2026-08-21-tiered-gates-shipped-2026-08-21-feat-tiered-gate.md`). This closes the
THEME-ALTITUDE half of §5.0 row 4, which that record already anticipated: *"the THEME altitude can
attach them now"*.

**REVIEW ROUND (2026-08-31, medium code-review — five findings applied, one refuted).**
1. **THE UNION WAS ON BY DEFAULT, which silently redefined a different measurement.**
   `load_detection_universe` feeds the exposure scan AND Component A / stage-2 residual
   detection. The scan reads each name's filings independently, so a wider population only adds
   names; detection builds CROSS-SECTIONAL factors — the SMB leg is a tercile of the population's
   caps — so unioning 810 names spanning $10B-$3.7T re-cuts those terciles and moves every
   existing primary name's residual, its clusters and its admission. Worse, `leaders.py`'s
   megacap slice is the SAME >$10B population, and its external-leader correlation assumes the
   megacap is NOT a cluster member — so a theme-band name could be designated leader of a cluster
   it had just joined, and "confirmed" by its own return. The default is now
   `include_theme_band=False`, with exactly ONE opt-in call site (the exposure scan), pinned.
2. A full `export_snapshots()` from a DB that never loaded the theme table would have written an
   EMPTY file over the committed theme rows — reachable via `vinci screen`, which full-exports
   without rebuilding first, and silent in both directions (nothing raised; the loader reads a
   present-but-empty file as "band not built"). Population tables now REFUSE to be truncated to
   zero, with the escape stated in the error. Pinned.
   **ADJACENT FINDING, RECORDED NOT FIXED:** `universe_snapshot` has the SAME hazard — a `vinci
   screen` on a checkout where no build has run would blank the committed PRIMARY population the
   same way. The guard is scoped to the theme table here because that is the one this change
   introduces and the one no build path seeds; extending it redefines three seeding tests whose
   fakes admit zero names (reproduced: they fail with `refusing to truncate
   universe_snapshot.jsonl from 1812 row(s) to zero`). Left for its own change rather than
   absorbed silently into this one.
3. The scan's "N primary + M theme-band" line printed BEFORE `--only-tickers`/`--max-names`
   narrowed the population — and since theme rows sort last, any `--max-names` under the primary
   count scanned zero theme names while announcing 810. Moved below the narrowing.
4. The theme band is rebuilt at **the primary snapshot's own vintage (2026-08-24)**, not four
   days ahead of it. Building ahead stamped ~954 identities `first_seen` after the committed
   universe's `as_of`, which trips #512's `identities_first_seen_after` guard on any backdated
   `run-weekly` — on CI too, since the seed loads the committed entity master before the check.
   Aligning the vintages also removes the spurious both-bands overlap the 4-day gap created.
5. The scan line now prints the theme band's OWN vintage beside its count
   (`themes/detection.py::theme_band_as_of`): the two bands are built by separate runs, nothing
   schedules the theme one, and a population ageing silently behind the primary is the
   stale-input class this repo keeps closing.
   REFUTED: SQL-injection risk in the band-routed table names (the value only ever comes from the
   `UNIVERSE_TABLES` whitelist); a lost single-generation/seed-before-export invariant; any
   decision-path leak through the store defaults.

**WHAT IT COSTS / WHAT IS ACCEPTED.**
- **MEASURED at this build, not inferred: META, NVO and AZN are ABSENT — dropped at `no_shares`**
  (no XBRL share frame for their CIK in the 5 recent quarter-instants; verified per name against
  the live frames). NVO/AZN is the known FPI wall (FPI1). **META is a US 10-K filer and is the
  MC1 class made concrete at the shares grain** — the tiered-gates record flagged megacap tag
  staleness as VERIFY-AT-BUILD; this is that verification coming back positive for the class. The
  band is not the constraint; the share-count source is, for a subset. They fail LOUDLY (counted
  in `no_shares`), never admitted at a fabricated cap. Fixing the shares source is a separate
  build — NOT started here (hold scope).
- Scan cost rises with the population: ~826 more names in the EFTS prefilter flood per cold scan
  (paced at 1 req/s per CIK-batch × phrase) and an LLM assessment per new match. Accepted — that
  is the point of the band; `--max-names` and `--only-tickers` still bound a run.
- The theme band is built on DEMAND (no scheduler wiring): `run_weekly` still builds the primary
  band only, so the theme snapshot ages until the operator rebuilds it. Deliberate — a second
  weekly build would double the EOD/EDGAR pull for a population nothing trades. Its rows carry
  their own `as_of`, so staleness is visible rather than silent.
